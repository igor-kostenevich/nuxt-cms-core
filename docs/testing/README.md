# Сценарії перевірки

Ручні сценарії, які автоматичні тести не покривають: взаємодія в браузері, кілька сесій, час (TTL),
закриття вкладки. Їх проходять перед релізом. Пізніше з них можна зробити e2e: зараз E2E немає
(MASTER_PLAN C-33).

## Формат

Один файл на область (`edit-mode.md`, згодом `media.md`, `forms.md`…). Кожен сценарій:

```
### EM-LOCK-02 — Забрати редагування
**Передумови:** …
**Кроки:** 1. … 2. …
**Очікувано:** …
**E2E:** так / ні — чому
```

- **ID** — `<область>-<тема>-<номер>`, не змінюється. Під цим іменем сценарій згадують у записах
  епіків, у баг-репортах і в назві e2e-тесту.
- **E2E: так** — сценарій детермінований і варто автоматизувати першим.
- **E2E: ні** — потрібні реальний час, сон ноутбука чи кілька пристроїв; лишається ручним.

## Коли додавати

Лише важливе: що ламає дані, доступ або головний сценарій, а також edge cases, які легко зламати
непомітно (кілька сесій, гонки, безпека). Дрібниці UI сюди не потрапляють.

- Епік з UI або з кількома сесіями додає свої сценарії разом із записом `docs/implementation/00N-*.md`.
- Баг, знайдений вручну, отримує сценарій, який його відтворює.

## Тестове середовище

- `npm run dev` → http://localhost:3000; локальний Supabase (`supabase start`).
- Акаунти з seed, пароль у всіх — `local-dev-password`:
  `owner@example.com`, `admin@example.com`, `editor@example.com`, `disabled@example.com` (вимкнений),
  `customer@example.com` (без доступу до CMS).
- Дві сесії одночасно: звичайне вікно + інкогніто, або два різні браузери.
- Studio: http://127.0.0.1:54323. Скинути дані до seed — `supabase db reset`.
