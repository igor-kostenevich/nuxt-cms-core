# 010d — Спрощення локалізації

Після 010 / 010b мультимовність працювала, але три місця коштували непропорційно багато:
- зміна основної мови конвертувала всі документи (rebase, ролі ревізій, межа R-20);
- елементи колекцій із коду перекладались за позиційними `default-N`: переставив дефолти — переклад
  поїхав на інший елемент;
- екран «Тексти» мав власний шлях запису (лише мова перекладу), а оригінал сторінок там не змінювався.

010d прибирає перше, стабілізує друге й робить «Тексти» другим входом у ті самі чернетки, publish і
lock, що й Edit Mode. Нових сутностей немає.

Рішення автора 2026-11-18 → MASTER_PLAN C-87…C-89. Свідомо **не** робили: окрему мову URL, hash
застарілих перекладів, чернетки текстів сайту, автоматичний реєстр (iframe, SSR, маніфест), translation
service / TranslationUnit, `legacyId`.

Джерела: MASTER_PLAN C-78, C-83…C-86; обговорення автора (аналіз спрощення, три раунди уточнень).

## Ключові рішення

**Мова оригіналу незмінна, конвертації немає.** Зміна основної мови переписувала всі сторінки, ревізії
отримували ролі, а поле з коду не мало «пустого» значення (R-20). Власнику це майже не потрібно. Тепер
перша мова — оригінал назавжди, мова без префікса в URL — теж вона, маршрутизація — Client. Захист і в
БД (тригери), а не лише відсутність кнопки. Колонку `revisions.base` і guard у `cms_page_restore`
лишили як legacy, прибрати — у 012.

**Явні id замість `legacyId`.** Затверджений спершу `legacyId` (читати за старою адресою, переносити ключ
при записі) ламався після матеріалізації: база зберігала масив із новим id, а переклади інших мов
лишались за `default-N`, і `applyTranslation` їх пропускав. Перенести ключі чужих мов при Save основної
мови неможливо. Небезпечним `default-N` робила позиція, а не сам рядок. Тому колекція з наявними
перекладами просто закріплює старі адреси явно: `{ id: 'default-0', … }`. Далі адреса стабільна всюди:
незбережені дефолти, масив у базі, published, draft, переклади, ревізії. Production-дані не
переписуються. Нові елементи мають змістовні id.

**«Тексти» не мають свого життєвого циклу.** Запис іде в ту саму чернетку `(page, locale)`, що й Edit
Mode, публікація — тим самим `cms_page_promote_draft`, конфлікти — тим самим lock. Щоб «Тексти» не стали
альтернативним редактором, що непомітно публікує чужі незавершені зміни:
- сервер приймає лише текстові листи зареєстрованих полів;
- діалог публікації показує, що в чернетці не лише тексти, і не позначає такі сторінки;
- публікація перевіряє версію чернетки під блокуванням.

Тексти сайту лишились «одразу» (C-85): UI лише чесно це підписує.

**Page-mutex — `FOR NO KEY UPDATE`, не `FOR UPDATE`.** Перевірка коду показала дві гонки:
- `cms_page_translate` блокував лише lock-рядки, яких могло не бути. Два записи читали ту саму
  чернетку, і другий затирав поле першого;
- `cms_page_lock_acquire` міг завантажити чернетку до коміту запису з «Текстів».

М'ютексом став рядок `cms_pages`. Але на нього посилаються FK п'яти таблиць, і кожна вставка (чернетка,
ревізія при кожному publish, published) бере `FOR KEY SHARE`. З `FOR UPDATE` Edit Mode, що тримає свій
lock-рядок і вставляє ревізію, чекав би м'ютекс, а «Тексти» з м'ютексом чекали б lock-рядок — deadlock.
Конкурентний тест це підтвердив: Postgres видав `deadlock detected`. `FOR NO KEY UPDATE` конфліктує лише
сам із собою, тож FK-перевірки не чекають.

Порядок блокувань скрізь: сторінка → lock-рядок → чернетка. Edit Mode RPC (save / publish / restore)
сторінку не беруть: з «Текстами» вони взаємовиключні через lock-рядок. Публікація кількох сторінок іде в
порядку ключів.

**Номер версії чернетки не вводили.** `updated_at` під `FOR UPDATE` рядка чернетки в тій самій
транзакції, що й promote, достатньо. Клієнт передає його рядком з API.

## Знайдено під час реалізації

- **`legacyId` не працював після матеріалізації** — замінено явними id (див. вище).
- **FK-deadlock із `FOR UPDATE`** — відтворено тестом, м'ютекс став `FOR NO KEY UPDATE`.
- **Overload `cms_language_publish(text)` лишився б доступним** — видалено явно, тест `pronargs = 1`.
- **`dblink` до самої бази:** у локальному Supabase `postgres` не superuser, тож потрібен пароль. Через
  сокет auth — trust, і dblink відмовляє. Тест з'єднується TCP на `inet_server_addr()` з паролем
  локального стека.
- **Помилка seed:** переклад послуги спершу був за адресою `services.strategy.title`, а ключ колекції —
  `services.items`. SSR показав англійський текст, виправлено.

## Обмеження й ризики

- `legacyId` немає: колекцію з перекладами за `default-N` розробник закріплює вручну, зберігши поточний
  порядок під час додавання id. Помилка в порядку дасть переклад не на тому елементі. Те саме було б і з
  `legacyId`, але тепер це видно в коді. Dev-попередження нагадує.
- Конкурентний тест потребує локального стека з паролем `postgres` (типовий для `supabase start`) і
  TCP-доступу бази до самої себе.
- `draftSummary` вважає «іншою зміною» будь-яку різницю поза текстовими листами реєстру. Поле, якого
  реєстр ще не знає (сторінку давно не відкривали в редакторі), теж стане «іншою зміною». Це безпечний
  бік: сторінка лише не буде позначена.
- Записи в одне поле з двох вкладок «Текстів» — виграє останній. Edit Mode відсікає lock.
- Сторінка з'являється на «Текстах» після першого відкриття в редакторі (реєстр не змінювався).

`/epic-review 010d`: критичних знахідок немає. Виправлено:

  блокувалась до перезавантаження. Тепер невдале значення не вважається надісланим.
- **`null` чи `''` при очищенні оригіналу** (A-2). Рішення бралось із `resettable` (є збережене значення

  ховало текст із коду. Тепер рішення лише за `inStoredList`. `null` для незбереженого листа в SQL —
  no-op.
- **Діалог публікації довіряв реєстру** (X-1). Реєстр пише клієнт, тож запис `hero.cta.href` як `text`
  робив зміну посилання «текстом», і сторінка позначалась для публікації. `draftSummary` тепер рахує
  текстом лише рядок (або відсутнє значення) з обох боків і не `href` / `mediaId` / `id` (як
  `cms_page_check_draft_shape`).
- Тести на мапінг `setTexts` / `publishLanguage` / `listContents` (маркер версії рядком без змін) — A-3.
- **`cms_page_set_texts` — лише тексти на рівні SQL** (міграція
  `20261121100000_cms_texts_text_only.sql`). Реєстр пише клієнт, тому підроблений або застарілий запис
  дозволяв змінити посилання, медіа, перемикач чи замінити об'єкт рядком. Довіреної схеми сторінки в
  Core немає (її власник — код Client, C-01), тож `cms_page_text_target` перевіряє те, чому можна
  довіряти:
  - останній сегмент — не нетекстова властивість формату примітива (`id`, `href`, `newTab`,
    `mediaId`, `focal`, `decorative`, `hidden`);
  - у збереженому оригіналі за адресою рядок або нічого;
  - жоден збережений предок не скаляр і не rich text документ.
  Переклад перевіряється за оригіналом, який перекладає. Те саме правило — у `isTextTarget`
  (`app/admin/texts.ts`): діалог публікації за ним рахує «тексти», а рядок, який сервер відхилить,
  стає лише для читання. pgTAP `cms_texts_text_only.test.sql`.
  **Межа:** адресу, якої оригінал ще не зберігає (поле показує значення з коду), без схеми не
  розпізнати. Там приймається лише ім'я листа, а рядок на місці об'єкта примітив ігнорує й показує
  дефолт. Поле з `field-key`, що закінчується на одну з цих властивостей, у «Текстах» не редагується
  (у перекладі `href` / `mediaId` / `id` відхилялись і раніше).
- **Позначка «не збережено»** біля рядка, запис якого впав: тост «Виправте позначені поля» посилався на
  позначку, якої не було.

`null` / відсутність — значення з коду. «Тексти» очищенням повертають до коду звичайне поле й елемент
колекції з коду (`null`). У збереженому списку коду вже немає, тож там лишається `''`. Навмисно
порожній текст поза списком задається в Edit Mode.
