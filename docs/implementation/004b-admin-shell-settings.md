# 004b — Admin shell + запис Site Settings

Другий зріз епіка 004: оболонка адмінки і перший запис у базу. Сутність і читання вже були
в 002, сесія і `cms_can('settings.update')` — в 003, компоненти форми — в 004a.

## Що зроблено

- `AdminShell`: темний сайдбар за макетом і світла шапка. Працюють Огляд (`/admin`) і
  Налаштування (`/admin/settings`). Решта пунктів видимі і нікуди не ведуть.
- Знак у сайдбарі — той самий «CMS» з i18n. Поруч назва сайту з `cms_site_settings`.
- Settings → General: `siteName`, `contactEmail`, `contactPhone`, `maintenanceMode`.
- `SettingsRepository.update()` і `toSettingsWrite()`. Порожня пошта і телефон
  зберігаються як `null`.
- Міграція `20261111010000_cms_site_settings_update.sql`: `update` лише для
  `authenticated`, і лише коли `cms_can('settings.update')`. Після ревʼю grant звужено до
  колонок форми: `id` і `updated_at` клієнт не пише.
- `AdminSwitch` для режиму обслуговування.
- Editor бачить форму вимкненою. Owner і admin зберігають.

Потік запису:

```
/admin/settings → useAdminSettings() → SettingsRepository.update()
                → session client → cms_site_settings (RLS)
```

Читання лишається анонімним клієнтом, як у 002. Сесійний клієнт імпортується лише
всередині `update()`, тож публічна сторінка не тягне `@supabase/ssr` через цей файл.

## Ключові рішення

**Оболонка — компонент, не Nuxt layout.** Ізоляція з 004a лишається на `AdminRoot`.
Логін оболонку не використовує. Пункти без екрана не є посиланнями: окремих
маршрутів-заглушок немає.

**Віджетів дашборда немає.** Огляд показує лише, хто увійшов. Пошук, аватар і картки
з макета — не цей зріз.

**Запис не розширює схему.** Колонки ті самі. `updated_at` виставляє тригер БД (після ревʼю;
спершу це робив репозиторій).
`insert` і `delete` як і раніше закриті: рядок один і вже існує.

**Порожній контакт — це `null`, не порожній рядок.** Колонки nullable. Пробіли
обрізаються. Назва сайту обов'язкова, пошта і телефон — ні, але якщо заповнені,
проходять ті самі правила, що й логін.

**Editor не пише, навіть якщо обійде форму.** Кнопка зникає, коли немає
`settings.update`. Політика все одно повертає нуль рядків, і репозиторій піднімає
`permission_denied`.

**Прапорець обслуговування лише зберігається.** Публічний сайт його ще не читає
як поведінку. Це 015.

## Перевірено

- Owner змінює назву, пошту, телефон і прапорець. Після збереження публічний `/`
  бачить нові значення. Порожня пошта стає `null`.
- Editor відкриває ту саму форму без кнопки збереження. Прямий `PATCH` із його JWT
  не змінює рядок.
- Anon, як і раніше, не може оновити рядок.
- Пункти Pages, Media, Forms, Analytics, Activity, Integrations, Users, Secrets
  не міняють адресу.
- Production HTML `/` не містить `@supabase/ssr` і не посилається на CSS оболонки.
- `npm test`, `npm run build`.

## Змінено пізніше

- `@vueuse/core`, доданий у цьому епіку, ніде не використовувався. Його прибрано з `dependencies`
  після ревʼю, бо він ставився б кожному Client. VueUse лишається дозволеною залежністю: його
  встановлює перший епік, якому знадобиться утиліта (MASTER_PLAN C-26).
- Після ревʼю: `updated_at` пише тригер БД, а не репозиторій (див. 002, «Змінено пізніше»).
  Міграцію цього епіку переписано на місці, окремої міграції поправок немає.

## Обмеження

- Немає підсторінок Settings, крім General.
- Немає пошуку, меню аватара і «View site» у новій вкладці: «Переглянути сайт»
  відкриває `/` у цій.
- `AdminSwitch` покриває лише стани, потрібні цій формі.

## Що свідомо не робили

Віджети дашборда, Brand, SEO, Social, Languages, Navigation, System, Analytics,
Users, Secrets, окремі маршрути для пунктів-заглушок.
