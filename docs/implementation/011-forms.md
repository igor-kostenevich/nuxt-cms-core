# 011 — Forms infrastructure

Форми сайту приймають заявки, а власник працює з ними в адмінці. Розробник оголошує форму в коді
(`cms.forms.ts`): поля, типи, правила. CMS форм не будує — вона приймає, зберігає й показує заявки,
дає їх архівувати, позначати спамом і вивантажувати. Сповіщень (Telegram) тут немає: це 013, форма
працює й без них.

Рішення автора 2026-11-19 → MASTER_PLAN C-90…C-95 (було D-31…D-36). План двічі пройшов зовнішнє рев'ю.
Свідомо **не** робили: конструктор форм, CRM-статуси («опрацьовано», відповідальний), вкладення,
UTM / referrer, автовідповіді, webhooks, CAPTCHA, outbox / черги, версіонування схеми форми.

Джерела: architecture.md §23; MASTER_PLAN §4 «011»; обговорення UX з автором (інбокс замість списку форм).

## Що зроблено

**Контракт форм (C-90, C-92):**
- `src/forms.ts`: `defineCmsForms`, `resolveCmsForms`. Помилкове поле чи форма відкидаються з
  попередженням під час збирання, як у `cms.texts.ts`. Ліміти: 100 форм, 50 полів, ключі з літери.
- `src/module.ts`: `cms.forms.ts` → шаблон `#cms/forms` (пишеться на диск: його імпортує й Nitro) +
  типи, watch; приватний `runtimeConfig.cms.supabaseSecret` (порожній під час збирання); типи хука
  `cms:forms:validate` для Nitro.
- `app/primitives/form-validation.ts`: `validateCmsForm` — нормалізація (trim, однорядкові поля без
  переносів, checkbox → boolean, порожні необов'язкові поля не зберігаються) і коди `required`, `type`,
  `email`, `tel`, `too_long`, `option`, `unknown_field`. Довжина рахується в символах, не UTF-16.
- `app/types/forms.ts` + експорт у `nuxt-cms-core/types`.

**БД — міграція `20261122100000_cms_forms.sql` (C-91, C-93):**
- `cms_can()`: `forms.view`, `forms.manage` — owner, admin.
- `cms_forms(key, enabled, updated_at, updated_by)`: insert `(key, enabled)`, update `(enabled)`,
  тригер ставить час і автора; RPC `cms_form_set_enabled` (security invoker — діють гранти й RLS).
- `cms_form_submissions`: `payload` jsonb ≤ 64 KB, `payload_fingerprint`, `location`, `read_at`,
  `page_path`, `locale`, `client_token`, `search_text`; unique `(form_key, client_token)`; без FK на
  `cms_forms`. Authenticated: select (`forms.view`), delete і update лише `location`, `read_at`
  (`forms.manage`). Індекси списку, форми й частковий для лічильника непрочитаних.
- `cms_form_rate_limits` — фіксовані вікна, доступ лише функції.
- `cms_form_submit` (security definer, execute лише `service_role`): advisory lock на
  `(form_key, client_token)` → повтор (fingerprint у SQL) → обмежене очищення старих вікон (лише для
  спроб, що рахуються; до лімітів) → лічильники відвідувача (якщо є `client_hash`) → загальна стеля
  форми `total:<form>` (50, лише для спроб, які пропустив ліміт відвідувача) → `enabled` → мова (лише
  активна) → insert у під-блоці. `client_hash = null` — без бакетів відвідувача; ліміти `null` — помилка.
- `cms_form_stats()` (security invoker): кількість, непрочитані, остання, сторінки.

**Відправка (C-91):**
- `server/api/cms/forms/[key].post.ts` — перший server route Core (каталог `server/` layer):
  форма з реєстру → `content-type` → тіло потоком ≤ 64 KB (413) → honeypot (тихий `ok`) → валідатор →
  хук сайту → адаптер. Відповіді `ok | invalid | unknown_form | disabled | rate_limited | too_large |
  bad_request | unavailable`; виняток у хуку → лог без значень і `unavailable`.
- `server/cms/supabase.ts`: server-only клієнт із secret-ключем (у т.ч. новий `sb_secret_*`), без
  cookies і сесії.
- `server/cms/form-store.ts`: server-only адаптер — виклик `cms_form_submit` і розбір статусів; маршрут
  не знає Supabase.
- `server/cms/client-address.ts`: джерело адреси відвідувача (`NUXT_CMS_CLIENT_ADDRESS`: `auto` / `none` /
  `socket` / `vercel` / `cloudflare` / `proxy[:N]`), нормалізація (IPv4-mapped → IPv4, IPv6 → /64),
  перевірка приватного peer для `proxy`, `hashClientAddress` — HMAC адреси. Жодному заголовку за
  замовчуванням не довіряємо; без адреси — `null`, а не спільний `unknown`.
- `server/cms/form-submit.ts`: чисті хелпери (потокове читання, розбір тіла, шлях сторінки, пошуковий
  текст, помилки хука).
- `app/composables/useCmsForm.ts`: стан, `submit`, `reset`, honeypot-поле, тексти (`label`, `option`,
  `fieldError`, `text`), `client_token` на логічну відправку. Відмова сервера у значеннях (`invalid`, у т.ч.
  `_form` / `resubmit`) скидає token: наступне натискання — нова відправка з тими самими значеннями;
  автоматичного повтору немає. `useCmsText` отримав `has()`.
- `.env.example`: `SUPABASE_SECRET` / `NUXT_CMS_SUPABASE_SECRET`, `NUXT_CMS_CLIENT_ADDRESS`;
  `package.json` → `files` + `server`. README: джерела адреси, retention заявок.

**Адмінка (C-94, C-95):**
- `app/data/repositories/forms.repository.ts` — лише методи сутності: список із фільтрами й пагінацією
  на сервері, експорт пачками, заявка, сусіди, зміна місця / прочитаності, «всі прочитані», видалення,
  лічильник, статистика, вимкнені форми, увімкнення.
- `app/admin/forms-view.ts`: прев'ю за ролями, контакти (посилання лише з перевірених значень і фіксованих
  схем), відповіді з fallback для полів, яких уже немає, людські назви сторінок, CSV.
- `app/admin/useAdminForms.ts`: тексти мовою оригіналу, лічильник для меню, огляд форм, список, заявка.
  Запити заявок приймають `enabled` (`can('forms.view')`): для інших ролей запитів немає, на SSR теж.
- Сторінки `/admin/submissions`, `/admin/submissions/[id]`, `/admin/submissions/forms`.
- `AdminShell`: пункт «Заявки» з лічильником (лише `forms.view`); на ширині < 768 px — висувне меню.
- `AdminInput`: `hideLabel` (як `labelPlacement: 'hidden'` у `AdminSelect`).
- i18n en / uk: `cms.submissions.*`, `cms.shell.menu` / `closeMenu`.

**Playground:** форми `contact` (усі типи полів, згода) і `newsletter` (лише email), компонент
`ContactForm` на `/about`, тексти форм у `cms.texts.ts`, Nitro-плагін із правилом «не більше двох
посилань у повідомленні».

## Ключові рішення

**Реєстр із коду замість синхронізації.** Форма існує, бо її оголосив код; БД зберігає лише те, що
змінив власник. Немає кроку синхронізації, який міг би перезаписати вимкнену форму після deploy, і форма
без жодної заявки одразу видна в адмінці.

**Повтор не рахується двічі.** Без advisory lock два одночасні запити з тим самим token обидва проходили
перевірку «вже є?» і обидва списували ліміт. Lock серіалізує їх до перевірки; unique лишається остаточним
захистом. Fingerprint рахує Postgres із `payload::text` (канонічний jsonb), тож розбіжності серіалізації
JS ↔ PG немає. Мутаційна перевірка: без lock конкурентний тест падає.

**Статус, а не exception.** `cms_form_submit` повертає `rate_limited` / `disabled`, а не кидає помилку:
інакше відкат транзакції стирав би і збільшений лічильник, і заблоковані спроби не рахувались би.

**Серверний ключ — лише для однієї функції.** Перевірку мови спершу зробив у маршруті читанням
`cms_languages`. Gate показав `permission denied`: у `service_role` немає доступу до таблиці. Права не
розширював — перевірка переїхала в RPC, яка й так працює від власника.

**Editor не бачить заявок.** Персональні дані; права на рівні колонок, а не лише RLS, тож навіть owner
прямим запитом не змінить `payload`, `form_key`, час чи token.

**Інбокс, а не список форм.** Власник приходить читати заявки, а не обирати форму. Одна форма — простий
список повідомлень; кілька — той самий список із фільтром.

## Знайдено під час реалізації

- **Шаблон `#cms/forms` не бачив Nitro** — збирання падало: шаблон жив лише у віртуальній ФС Vite.
  `write: true`.
- **`service_role` без доступу до `cms_languages`** — див. «Ключові рішення».
- **Builder PostgREST повертався з `async`-функції** — thenable, тож `await` виконував запит до
  сортування й пагінації. Знайшов typecheck; запит тепер будується синхронно.
- **Адмінка не мала мобільної розкладки** — на 360 px горизонтальний скрол на кожному екрані. Висувне
  меню в `AdminShell` (C-95).
- **`nitropack/runtime` не імпортується явно** — це не залежність Core; серверний код бере
  `useRuntimeConfig` / `useNitroApp` з auto-imports Nitro.
- **Міграцію форм змінено після першого локального застосування** (мова в RPC); функцію в локальній базі
  оновлено вручну, `supabase db reset` дає ту саму схему з файлу.
- **UX-правки автора:** людські назви сторінок замість шляхів; тексти без назв файлів і «deploy»; ключ
  форми прибрано; «Поля» на екрані форм прибрано (інформація без дії); екран — «Керування формами».

## Обмеження й ризики

- **Адреса відвідувача для лімітів** (R-10, C-91). За замовчуванням (`auto`) — `vercel` на Vercel, `socket`
  у dev, інакше `none`: тоді діє лише стеля форми, і один відправник може вичерпати її для всіх на вікно.
  Self-hosted — `proxy[:N]` (лише з приватного peer) або `socket` без проксі; Cloudflare — лише коли origin
  закритий для інших. Netlify й інші платформи — `none`, доки заголовок не перевірено (016).
- Хук `cms:forms:validate` працює до лімітів: його відмови не рахуються (C-92).
- Автоматичного строку зберігання заявок немає; retention — рішення сайту (README).
- Ліміти в Postgres — для звичайного спаму. Масована атака навантажує саму БД; захист на рівні edge —
  поза Core.
- Назва сторінки в адмінці береться з адреси («About», «Web design»); справжніх назв сторінок у Core немає.
- Навмисно порожній текст поля форми задає лише розробник; адмінка заявок не змінює.
- Сповіщень немає до 013: власник дізнається про заявку, зайшовши в адмінку (лічильник у меню).
