# 010 — Localization v2

Контент сайту став мультимовним. Мови живуть у базі, тож нова мова не потребує migration чи deploy.
Сторінка перекладається в Edit Mode тією самою сторінкою Client. Публічний сайт читає мову одним
запитом: неперекладене береться з мови за замовчуванням. Маршрутизацію локалізованого сайту робить
Client, Core дає лише дані.

> *Змінено в 010d* ([запис](./010d-simplify.md)): зміну мови за замовчуванням із конвертацією, ролі
> ревізій в UI й R-20 прибрано — мова оригіналу незмінна (C-87). Опис нижче — стан на кінець 010.

Рішення закрито перед планом і перенесено в MASTER_PLAN §2 як C-78…C-83 (було D-27, D-28, D-29, D-30,
D-60; право мов — нове). Пропущене — у реєстрі TODO (MASTER_PLAN §3), межа моделі — R-20.

Джерела: architecture.md §21; Б9 (v2 + §22 «Доповнення»); Б3 §27; Б10 §3. Дизайн Settings → Мови —
приблизний скріншот автора: sub-nav Settings, картка мов. Його змінено під рішення: без перемикача
«Enable multilingual» (C-81) і без «Remove», бо мова лише вимикається. Перемикач мов у тулбарі зроблено в
стилі page switcher.

## Ключові рішення

**Переклад — плаский об'єкт листів, а не друге дерево (C-78).** Пропонований аудитом окремий спільний
документ означав би нові таблиці, переписані save / publish / restore і розщеплення наявних документів
за типами полів, яких сервер не знає. Натомість база — це наявний документ мови за замовчуванням, а
переклад зберігає лише те, що перекладається: текст, rich text, `label`, `alt`. Ключ — адреса поля
(C-48). Для лінка й зображення адреса має суфікс (`hero.cta.label`), тож мова змінює лише свою частину
значення. Таблиці, RPC Draft / Publish / Lock і формати значень primitives не змінились. Застосування
перекладу не потребує типів: лист пишеться туди, де адреса резолвиться, об'єкти створюються, а
елемент колекції — ні. Тому лист видаленого елемента просто пропускається, а Save його прибирає.

**Структуру редагує лише мова за замовчуванням.** Інакше публікація перекладу змінювала б інші мови
(колекції, картинки) і ламала б C-46. У мові перекладу Engine ігнорує не-листові зміни навіть через
API панелі. UI показує їх disabled з поясненням, а не ховає: редактор бачить, де це змінити.

**Fallback — не налаштування.** На рівні поля fallback на базу закладено в модель. На рівні сторінки
Core віддає `translated` і `locales`, а показати, 404 чи noindex, вирішує Client: playground ставить
`noindex`. Прапорець у config дублював би рішення, яке Client однаково приймає в роутингу.

**Мова сторінки — стан, який ставить Client (`useCmsLocale`).** Core не знає URL-схеми. В Edit Mode
middleware Client не працює (C-59), тому мову ставить редактор, і Client-код читає її звідти ж. `null`
означає мову за замовчуванням, тож одномовний Client нічого не налаштовує, а зміна default не ламає
його.

**Внутрішні href — нейтральні, резолвер — runtime Client (C-79).** Варіант «редактор вписує `/en/about`
у кожній мові» множить ручну роботу. Варіант «Core префіксує за config» нав'язує URL-схему. Резолвер
зберігається на `nuxtApp`, тож на сервері він окремий на кожен запит. Його результат знову проходить
allow-list.

**Зміна мови за замовчуванням — конвертація в одній транзакції.** Для кожної сторінки окремо для
Published і Draft:
- нова база = стара база + переклад нової мови;
- переклад старої мови = значення старої бази за адресами цього перекладу.

Кожна мова показує те саме, що до зміни. Межа — R-20: поле, якого база ніколи не мала (дефолт із коду),
не має «пустого значення» для старої мови. Тому після зміни стара мова показує там текст нової. Діалог
підтвердження про це каже.
- Поки будь-яка сторінка відкрита в Edit Mode, RPC повертає `conflict`: відкрита сесія тримає
  документ у старих ролях. Протерміновані lock'и видаляються, тож стара сесія отримує `lock_lost`, а не
  зберігає старі ролі поверх нових.
- Ревізії не переписуються. Ревізія пам'ятає роль, і restore ревізії іншої ролі повертає `conflict`.

**Перша мова — default, і лише вона.** Поки таблиця порожня, сайт має віртуальну мову з `cms.config.ts`.
Перше «Додати» в адмінці спершу зберігає її як default, бо наявний контент написаний нею, і лише потім
додає нову. RPC це перевіряє: default задається лише першою мовою або через `set_default`.

**Settings — розділ з меню, бо так на скріншоті.** Бренд переїхав на окрему сторінку. Пункти, яких ще
немає (SEO, Social, Navigation), у меню не показано: stub-и в sub-nav лише шум.

## Після перевірки автором

- **↑ / ↓ у Settings → Мови падали з `21000 UPDATE requires a WHERE clause`.**
  - Причина: Supabase вантажить для API-запитів `safeupdate`, і `UPDATE` / `DELETE` без `WHERE`
    відхиляються навіть у security definer функціях.
  - Те саме чекало `cms_language_set_default` на `delete from cms_page_locks`.
  - Виправлено: явні `WHERE` у міграції.
  - pgTAP цього не бачить, бо працює як postgres без `safeupdate`. Тому є статичний тест
    `tests/migrations-safeupdate.test.ts`: кожен `UPDATE` / `DELETE` у міграціях має `WHERE`.
- **Пошук мови без кодів.**
  - Опції показують назву мовою адмінки й назву самою мовою; друга ховається, якщо збігається.
  - Код усе одно знаходить мову.
  - Кращі збіги першими: на «ru» спершу Russian, а не Belarusian, що лише містить «ru».
  - Select мови за замовчуванням теж без кодів.
  - Тест `tests/admin-languages.test.ts`.

- **Settings → Мови спрощено за відгуком автора.**
  - Один список і кнопка «+ Додати мову» в шапці. Вона відкриває popover з пошуком, і клік по мові
    одразу її додає (`AdminLanguageCombobox`).
  - Select основної мови, рядок стану й абзаци пояснень прибрано. «Зробити основною», «Вище» /
    «Нижче» перенесено в меню `⋯` рядка (`AdminMenu`).
  - Порядок змінюється drag'ом за ручку, з клавіатури — стрілками на ручці. Ручка не стає disabled
    під час збереження, тож фокус не злітає.
  - Пояснення стали тултіпами (switch основної мови, бейджі «Основна» / «Вимкнена») або перейшли туди,
    де вони потрібні: у повідомлення після додавання й у діалог підтвердження.
  - Коди мов у рядках прибрано. Порожній стан «Сайт одномовний…» — коли мова одна.

- **Перемикання мови «смикало» сторінку.**
  - Алерт результату з'являвся над списком і зсував його.
  - На час запиту всі контроли ставали disabled.
  - Тепер результат дій показує тост (`AdminToasts` в оболонці адмінки, `useAdminToast()`). Логіку
    тостів винесено з Edit Mode у спільний `app/admin/toasts.ts`.
  - Switch перемикається одразу і повертається, якщо запит упав.
  - Блокується лише дія, що виконується; клік поруч під час запиту ігнорується.
- **Назва мовою самої мови могла бути не тією мовою.** Chrome без даних для локалі (напр. `sq`) відповідає
  мовою інтерфейсу, тож у базу потрапляло «Албанська». Тепер такий випадок дає англійську назву.

- **Мова «в роботі».** Нова мова додається прихованою (`cms_language_add` → `active = false`, крім
  першої).
  - Приховані мови бачать усі з `pages.edit` (RLS), тож вони є в перемикачі Edit Mode з міткою
    «прихована на сайті» (`app/editor/languages.ts`).
  - У Settings → Мови switch означає «На сайті», бейдж — «В роботі». У меню `⋯` з'явився пункт
    «Перекласти в редакторі». Тост після додавання підказує наступний крок.
  - Settings → Загальні показує назву сайту й для прихованих мов.
- **Неперекладені поля в Edit Mode.**
  - Синя пунктирна рамка позначає поля, що ще показують основну мову: `engine.untranslated` /
    `isUntranslated`, без фонів і декоративних зображень.
  - У банері перекладу — «Лише неперекладені (N)»: затемнює решту через ту саму маску Overlay.
  - Лічильників-прогресу немає (рішення автора).
  - Стани мов у перемикачі вантажаться, щойно сторінка готова.
- **pgTAP ізольовано від живих lock'ів.** Тест зміни мови за замовчуванням падав, поки в локальній базі
  була відкрита сесія Edit Mode. Тепер фікстура прибирає lock'и (транзакція відкочується).
- **Друк у мові перекладу лагав.**
  - Кожна літера перебудовувала весь документ із бази (клон) і для кожного поля перевіряла
    `canTranslate` через ще один клон.
  - Тепер Engine пише змінений лист у показаний документ на місці, як в основній мові. Перевірка йде
    через `canSetAt` (`app/primitives/paths.ts`) без копій.
  - Результат: близько 1 мс на символ.
- **Переклад елемента колекції з коду зникав після blur.**
  - Якщо основна мова ще не зберігала колекцію, `canTranslate` пропускав адресу: шлях «прокладався»
    звичайними об'єктами, а колекція такий переклад не відмальовує.
  - Тепер елемент колекції, якого немає в базі, не перекладається. Панель показує «Спершу збережіть
    основною мовою», як і задумано в C-78.
  - Тести: `canSetAt` ↔ `setAt`, колекція поза базою, запис на місці.
- **Видалення мови (рішення автора, змінює C-15 / C-83).**
  - RPC `cms_language_delete`: owner. Основну мову видалити не можна; поки сторінка відкрита в Edit
    Mode, повертає `conflict`.
  - Видаляє мову разом із чернетками, опублікованими перекладами, ревізіями й назвою сайту цією
    мовою.
  - В адмінці — червоний пункт «Видалити мову» в меню `⋯`, відділений лінією. Діалог «Видалити
    назавжди» пояснює, що зникне, і нагадує, що мову можна просто сховати.
  - pgTAP: права, основна мова, lock, повне прибирання.
- **Назва сайту іншими мовами згорнута.** Одне поле «Назва сайту» і під ним згортка «Назва іншими
  мовами · заповнено N з M» з компактними рядками «мова → поле».
- **Каталог мов скорочено** до ~30 поширених (Європа + кілька світових). Будь-яку іншу можна додати
  кодом.
- **Назви сайту для прихованих мов читаються сесійним клієнтом.** Публічна політика тепер віддає лише
  активні мови, тож адмін-форма читала порожнечу.
- **Наступний зріз — 010b** (MASTER_PLAN §4): реєстр полів, «Тексти сайту», екран «Переклади».

## Після аудиту 006–012 (2026-11-22)

- **Приховану мову читав будь-який залогінений користувач.** Політики `cms_page_published_select_cms` і
  `cms_site_settings_translations_select_cms` мали для `authenticated` `using (true)`. Задум, як у
  коментарі міграції, — «CMS-користувачі бачать усі мови». Але `authenticated` — це й customer сайту
  без рядка в `cms_users` (та сама Supabase Auth), і вимкнений CMS-користувач. Обидва прямим запитом,
  а також через `cms_page_get_editable`, читали опублікований переклад і назву сайту прихованої мови
  (відтворено). Це порушувало C-83.
  - Тепер `authenticated` бачить те саме, що anon (активні мови або bootstrap без мов), плюс усі мови
    з `cms_can('pages.edit')`, як уже було в `cms_languages` і `cms_site_texts`.
  - Edit Mode, «Тексти» і Settings працюють під CMS-ролями, тож нічого не втратили.
  - Міграцію виправлено на місці, локальну БД — `alter policy`, без reset.
  - pgTAP `cms_hidden_languages.test.sql`: anon, customer, disabled, editor, owner, editable read,
    bootstrap. Зі старою політикою падають усі п'ять негативних перевірок.
- **Переклад міг змінити структуру.** `cms_page_check_draft_shape` перевіряла формат адреси й тип
  значення, але не те, що лежить за адресою в оригіналі. Editor із lock через `cms_page_save_draft`
  записав у чернетку мови (відтворено):
  - `quote.visibility.hidden` — `CmsOptional` ховає блок за будь-яким truthy;
  - `hero.cta.newTab: "false"` — `CmsLink` перевіряє truthy;
  - рядок замість цілого значення лінка чи optional;
  - ключ усередині rich text документа;
  - рядок замість rich text.

  Опублікувати таке міг лише owner / admin, але в Edit Mode підміну видно лише як зміну сторінки.
  Виправлено без зміни формату (C-78, інваріант «переклад змінює лише тексти»):
  - SQL `cms_page_text_fits(doc, address, value)` у міграції `cms_texts_text_only`.
    `cms_page_text_target` («Тексти») тепер — її рядковий випадок, поведінка та сама;
  - `cms_page_check_translation` у `cms_page_save_draft` перевіряє нові й змінені листи мови перекладу
    проти оригіналу (draft ?? published основної мови) і відхиляє `22023`. Незмінений старий лист, під
    яким оригінал змінився, збереження не блокує. Restore не перевіряється: це збережена ревізія;
  - TS `translationFits` — те саме правило. `applyTranslation` пропускає лист, що не пасує, а
    `pruneTranslation` (Save в Edit Mode) його прибирає.

  Легальні переклади не змінились: текст, `label`, `alt`, rich text, елементи колекцій за id, поля з
  дефолтом у коді. Тести:
  - pgTAP `cms_translation_texts.test.sql` (20) — паритет із фікстурою
    `tests/fixtures/translation-fits.json`, запис через RPC, старий лист, оригінал без обмежень. Зі
    старою `cms_page_save_draft` падають 11 перевірок;
  - vitest `translation.test.ts` — ті самі кейси, читання, prune.

  Межа: адресу, якої оригінал не зберігає (значення з коду), без схеми сторінки не типізувати. Вона
  приймається за іменем, а примітив на значення не того типу показує дефолт. Рядок там, де код чекає
  rich text, `CmsRichText` теж показує як дефолт. Навпаки, документ чи об'єкт на текстовій адресі
  `CmsText` показує як дефолт: він рендерить лише рядок, `''` теж (`tests/cms-text.test.ts`).

## Обмеження

- R-20: див. вище.
- Зміна мови за замовчуванням не створює ревізій. Остання ревізія може не дорівнювати Published, доки
  сторінку не опублікують знову (виняток із C-51).
- Перекладаються лише сторінки й `site_name`. Header / footer — код Client (C-63). Колекції 014
  отримають `*_translations` за C-15.
- Client-код в Edit Mode має брати мову з `useCmsLocale()`, а не з `route.params`: його middleware там
  не виконується.
- Каталог мов в адмінці вбудований (~70 кодів). Назви дає `Intl.DisplayNames`, тож рантайм без
  потрібних даних покаже код.

## Що свідомо не робили

- AI-переклад, кнопку «Translate», ручні статуси і `outdated` (anti-scope).
- Lock на мову: lock спільний на сторінку (C-54).
- Локалізований `default_alt` медіа (C-80).
- `@nuxtjs/i18n` і URL-схему в Core.
- Окремий прапорець fallback у `cms.config.ts`.
