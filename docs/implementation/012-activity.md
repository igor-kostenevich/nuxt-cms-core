# 012 — Activity

Журнал активності — простий захищений список важливих дій у CMS. З нього можна перейти до зміненого
об'єкта або до опублікованої версії сторінки в History. Власник і адміністратор бачать, хто, що й коли
змінив; редактор журналу не бачить.

Рішення автора 2026-11-19…21 → MASTER_PLAN C-96 (було D-37). План спрощено після зовнішнього аналізу:
3 зрізи, 11 полів, без групування подій.
Свідомо **не** робили:
- diff версій і попередній перегляд ревізії;
- окремий Restore з журналу;
- логування Save draft і текстів сайту;
- групування масових операцій (parent / child);
- строк зберігання журналу;
- фільтр «Мої дії»;
- запис журналу з браузера.

Джерела: architecture.md Б8 §27, Б10 §28, Б11 §22, Б14 §36, Б21 §35, дизайн-ТЗ §7; MASTER_PLAN §4 «012».

## Що зроблено

**012a — дані (`supabase/migrations/20261123100000_cms_activity.sql`):**
- `cms_activity` — 11 полів:
  - `id`, `created_at` (`clock_timestamp()`: події однієї транзакції зберігають порядок);
  - `actor_id` (`on delete set null`), `actor_email` — знімок;
  - `action`, `entity_type`, `entity_id` (text: uuid, код мови, ключ форми), `entity_label` — знімок назви;
  - `locale`;
  - `revision_id` (`on delete set null`);
  - `details` — об'єкт ≤ 4 KB.
- Індекси `(created_at desc, id desc)` і `(entity_type, created_at desc, id desc)`.
- Доступ:
  - клієнтські ролі мають лише `select`, RLS за `cms_can('activity.view')` (owner, admin);
  - insert / update / delete недоступні жодній клієнтській ролі, зокрема `service_role` і CMS-owner.
  - Пише лише власник таблиці через `cms_activity_log` (security definer, execute відкликано в усіх
    клієнтських ролей).
- Події пишуться в транзакції самої дії:
  - **insert у security definer RPC:**
    - `cms_page_promote_draft` — одна точка для Publish і «Опублікувати переклад»;
    - `cms_page_restore`, `cms_page_lock_force_unlock` (лише коли lock був);
    - `cms_media_create` / `replace` / `delete`;
    - `cms_language_add` / `delete` / `set_active` (лише фактична зміна).
  - **Тригери (security definer) на прямих записах через RLS:**
    - `cms_forms` — фактична зміна `enabled`; перша пауза — це INSERT з `false`;
    - `cms_site_settings` — одна подія на рядок, allow-list полів;
    - `cms_site_settings_translations` — INSERT / UPDATE назви;
    - `cms_form_submissions` — statement-level з transition tables:
      - рахуються лише рядки, де справді змінилось `location`;
      - для delete — кількість;
      - `read_at` і no-op подій не створюють.
- `details` налаштувань — лише назви полів. Значення «було → стало» є тільки в `maintenance_mode`.
  Контакти, назва, media id і секрети не записуються.
- Право `activity.view` у `cms_can()` і `app/auth/permissions.ts`.
- Прибрано legacy `cms_page_revisions.base` і guard у Restore (TODO 010d).
- `supabase/seed.sql`: ревізії без `base`. Наприкінці seed очищає журнал, бо дані seed — не дія команди.

**012b — екран:**
- `app/data/repositories/activity.repository.ts` — лише `list()`:
  - keyset за `(created_at, id)`;
  - курсор — точний рядок часу з БД, без JavaScript `Date`;
  - перед підстановкою у фільтр курсор перевіряється за форматом.
- Нові функції в наявних repositories, для посилань:
  - `PagesRepository.editPaths(ids)`;
  - `FormsRepository.existing(ids)` — посилання на заявку лише поки вона існує.
- `app/admin/activity-view.ts` — підписи подій (безособові: «Опубліковано…», «Повернуто версію… у
  чернетку»), посилання, групування за днями. Правила посилань:
  - лише фіксовані адмін-маршрути;
  - лише перевірені id;
  - лише за правом на ціль;
  - видалені назавжди заявки й видалені файли — без посилання.
- `app/admin/useAdminActivity.ts`: перша сторінка — `useAsyncData` (SSR), «Показати ще» дозавантажує на
  клієнті. Без `activity.view` запитів немає.
- `/admin/activity`: категорії Усе / Сторінки / Медіа / Налаштування / Заявки (у URL), «Сьогодні» /
  «Вчора» / дата, порожній стан, помилка, mobile. Пункт меню — лише з `activity.view`.
- Сервер і гідратація показують час і дні в UTC, після mount — у поясі браузера: сервер не знає пояс
  переглядача, а однаковий рендер прибирає hydration mismatch.

**012c — зв'язок з History:**
- Посилання з подій `publish` / `restore` з ревізією: `/admin/edit<edit_path>?locale=…&history=<id>`.
  Без ревізії (видалена разом із мовою) відкривається лише сторінка.
- `EditorRoot`: `?history=` відкриває History, коли сторінка готова, — один раз на завантаження, як
  `?field=`.
- `HistoryPanel`:
  - ревізія є в останніх 50 — підсвічена;
  - старша — `PagesRepository.getRevision(id, key, locale)` показує її окремим рядком «Версія з журналу
    активності» з тим самим Restore. Сторінку й мову перевіряє сам запит (`page:cms_pages!inner(key)`,
    `.eq('page.key')`, `.eq('locale')`), а id не у форматі uuid не робить запиту;
  - не знайдено — підказка, редактор працює далі.
- Restore — наявний: Content Lock, `replace_draft`, підтвердження.
- `EditorRepository` (мінімальний Draftable-контракт, C-60) отримав обов'язковий `getRevision`. Колекції
  з Draft у 014 реалізують його так само.

## Ключові рішення

**Запис у БД, а не з браузера.** Журнал, який пише клієнт окремим запитом, можна обійти прямим
викликом API. Тому події пишуть RPC і тригери в тій самій транзакції: збій журналу відкочує дію.

**Тригер — там, де адмінка пише напряму.** Налаштування, заявки й `cms_forms` (`cms_form_set_enabled` —
security invoker) змінюються через RLS. Тригерні функції — security definer, інакше виклик закритого
logger від `authenticated` упав би.

**Масова дія — одна подія без нової RPC.** Адмінка вже змінює заявки одним SQL-запитом
(`.in('id', ids)`), тож statement-тригер дає одну подію з кількістю. `UPDATE OF location` з transition
tables несумісний, тому зміну перевіряє сама функція.

**Diff і Restore не дублюються.** Activity лише веде до History, де Restore уже є з lock і
підтвердженням. Порівняння версій, якщо знадобиться, логічніше будувати в History.

**Без Save draft і текстів сайту.** Обидва зберігаються часто (тексти — на blur кожного поля), тож
журнал заповнився б сотнями малокорисних подій. Важливо, коли зміни пішли на сайт і хто це зробив.

## Знайдено під час реалізації

- **Однаковий `now()` в одній транзакції** давав випадковий порядок подій («Опублікувати переклад», тести).
  Default `created_at` — `clock_timestamp()`.
- **Restore версії, яка дорівнює Published, прибирає чернетку** (C-53) — тест спершу цього не враховував.
- **`seed.sql` вставляв `base`** — reset падав; без reset це не спливло б.
- **Seed записував подію налаштувань без автора** — тригер на перекладах назви сайту; seed очищає журнал.
- **SSR форматував час у поясі сервера** — розбіжність із браузером за будь-якої різниці поясів, не лише
  на межі доби. Перша перевірка її не показала: інструмент браузера не передавав `console`; перевірку
  переписано через CDP.
- **Зелена точка «на сайті»** у рядка старої версії (правило `:first-child`) — виправлено стилем.

## Обмеження й ризики

- Посилання на сторінку веде на `edit_path` — шлях, де її востаннє відкривали в редакторі. Після зміни
  маршруту в коді він застаріває (як на «Текстах»).
- «Показати ще» не переживає «Назад»: дозавантажене не зберігається в URL.
- До mount час показується в UTC — короткий перехід на локальний.
- Тіла дев'яти RPC перевизначено повною копією: наступна зміна має брати версію з міграції 012, інакше
  подія тихо зникне (pgTAP це впіймає).
- Збій logger відкочує саму дію — свідомо.
- Email видаленого користувача лишається в журналі; строку зберігання немає (R-21, TODO).
- Конкурентні pgTAP-тести (dblink) лишають події «concurrency-fixture» в локальній БД (TODO).
- Екран зібрано без макета, у стилі «Заявок».
